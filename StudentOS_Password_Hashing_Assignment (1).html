Secure Password Storage Using Multi-Algorithm Hashing

Project: StudentOS – Student Academic Productivity Dashboard

Aim

To remove plain-text password storage from StudentOS and save every password only as a salted hash, using a choice of hashing algorithms.

Problem in the original system

The login page saved passwords as readable text in the browser's LocalStorage, so anyone opening Developer Tools could read them.

Solution

A hashing module (vault.js) built on the browser's Web Crypto API. A password is normalised, combined with a random salt, passed through the chosen algorithm, and only the resulting hash is stored together with the algorithm name, so login can repeat the same steps and compare results.

Passwords are never saved as text. Each one is turned into a salted hash, and you choose which algorithm does it. The record stores the algorithm name, so every user can use a different one and still sign in.

Algorithms included

  1. PBKDF2-SHA256 / SHA384 / SHA512: the standard password-stretching function with three different underlying hashes.
  2. Cascade: PBKDF2-SHA512, then HMAC-SHA256 keyed by the salt, then a chain of SHA-384 rounds. Three different primitives in series.
  3. Salted SHA-512 chain: repeatedly hashing the previous output with the salt. Included to show the idea; PBKDF2 is the stronger choice.
  4. Every algorithm gets a random 16-byte salt, and the result is then sealed with a device key that the browser stores as non-extractable.

A single plain SHA-256 or MD5 pass is deliberately not offered: those are built to be fast, which makes passwords easy to brute-force. Password hashes need to be slow on purpose.

Use it in login.html

  1. Save the script at the bottom of this file as vault.js (everything from const Vault to the final })();). A ready-made copy is provided separately. Load it before your other script: <script src="vault.js"></script>
  2. Registration (make the handler async). Pick an algorithm by name:
const passwordHash = await Vault.hash(password, 'pbkdf2_sha512');
const newUser = { name, university, major, email, passwordHash };   // no "password" field
  1. Login:
const wait = Vault.lockedFor(email);
if (wait) { showToast(`Too many attempts. Try again in ${wait}s`, 'danger'); return; }

let ok = false;
if (foundUser.passwordHash) {
  ok = await Vault.verify(password, foundUser.passwordHash);   // reads the algorithm from the record
} else if (foundUser.password !== undefined) {                  // old plain-text user: upgrade now
  ok = Vault.constantTimeEqual(foundUser.password, password);
  if (ok) {
    foundUser.passwordHash = await Vault.hash(password, 'pbkdf2_sha512');
    delete foundUser.password;
    localStorage.setItem('studentos_users', JSON.stringify(users));
  }
}
if (!ok) { Vault.fail(email); showToast('Invalid password!', 'danger'); return; }
Vault.succeed(email);

Limit to know about: StudentOS has no server, so hashing happens in the user's browser. It stops passwords being read or reused from storage, but cannot stop someone with full control of that browser. Real accounts need a backend (Node + bcrypt/argon2), which suits your MERN projects.

Testing summary

  1. Registering a user stores only a value of the form sos2$algorithm$rounds$pepper$salt$hash; no password text is saved.
  2. Two users with the same password receive completely different hashes because each has its own random salt.
  3. Correct password: sign-in succeeds. Wrong password: sign-in is rejected.
  4. Repeated wrong attempts trigger a growing delay before the next try.
  5. An old plain-text user is converted to a hash automatically on first login.

Conclusion

Storing salted, slow hashes instead of passwords means a leaked or inspected LocalStorage does not reveal what users typed. Because StudentOS is a frontend-only project, a server-side implementation (Node.js with bcrypt or argon2) is the recommended next step for production use.
